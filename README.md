# SoL-Astr

给模型一个压缩工具。话题聊完了它自己调 `sol_astr_compact`，插件现场算一笔账：划算就把早前的对话换成一段摘要，不划算就原样退回并说明原因——判断本身不做任何 LLM 调用，一分钱不花。算法移植自 NVIDIA Research [SoL-Pi](https://nvlabs.github.io/SoL-Pi) 的 Online Context Compact（没有论文，以[源码](https://github.com/NVlabs/SoL-Pi/tree/main/src/sol-pi/extensions/online-context-compact)为准）。

## 和内置压缩的关系

插件管早压，内置 82% 管防爆，两层都留着。

- 内置 82% 压缩：别关，那是兜底（核心 `LLMSummaryCompressor` 的 `compression_threshold = 0.82`，compressor.py:131）
- 单条工具结果 overflow：不受影响
- 按轮截断 `max_turns`：不是 -1 会抢在压缩前面丢轮，面板会告警，插件不动它

## 面板

插件页打开 dashboard，全部信息都在：

- 标尺：保留段、窗口保护线、核心 82% 兜底线和各会话真实用量画在同一根对数轴
- 现场判账：拿用量最大的会话算一笔——压一次花多少、每轮少花多少、第几轮打平、估计还能聊几轮、判压还是不压、为什么
- 两个模型解析到了 OpenRouter 哪条目录、四个价格
- 模拟器：拖保留段 / 归档段 / 每轮增量，看这笔账怎么判，保留段能直接写进配置
- 台账：压缩率、outcome 分布、归档段分布、每次压缩的前后对比和耗时
- 告警：能让插件悄悄失效的事（人格白名单挡工具、`max_turns` 抢跑、拿不到价目）

## 配置

摘要模型和压缩提示词不在插件里，读核心「上下文管理策略」那两项，留空就回落当前聊天模型和插件默认。压缩模型挑个比主模型便宜快的：摘要是回复前同步做的，让主模型干这活，用户每轮多等十几秒，账也算不回来。

插件自己的四项，面板里能改：

| 配置项 | 默认 | 说明 |
|---|---|---|
| `enable_compact` | false | 总开关 |
| `dry_run` | true | 影子模式，账照算、不动历史 |
| `keep_recent_tokens` | 0 | 保留段，0 = 20000（上游 `DEFAULT_KEEP_RECENT_TOKENS`，extension.ts:35） |
| `strip_tool_trace` | true | 压缩轮落盘前删掉工具调用记录 |

没有压缩线、没有阈值比例、没有预期轮数——这些都不需要你填，见下一节。

## 判账怎么判

先对齐名词。一次压缩把上下文切成三段：**保留段**是最近的几轮，原样不动；**归档段**是保留段之前的全部旧对话，整段交给摘要模型，压成一段摘要替换回去；当前这轮永远保留。

插件里没有「压缩线」。每次话题边界（模型调用工具）现场做一道除法（economics.py，逐行对应上游 economics.ts）：

```
打平轮数 = 一次性成本 ÷ 每轮少花
一次性成本 = (保留段+memo)×(输入价−缓存读价+缓存写价) + memo×摘要输出价 + 归档段×摘要输入价
每轮少花 = (归档段−memo)×缓存读价
估计轮数 = (窗口−当前用量) ÷ 每轮平均增量     ← 增量从本会话历史实测
打平轮数 ≤ 估计轮数 → 压，否则 → 退回原因
```

三条补充规则，全部来自上游：

1. **首次压缩**视野 ×2（`firstCompactionRequestScale`，economics.ts:18）；聊天里视野就是窗口封顶本身，×2 恒被吃掉，公式保留。
2. **后续压缩更严**：打平轮数 ×1.5（`subsequentCompactionMargin`，economics.ts:19）仍要 ≤ 估计轮数，且上一次压缩没还完的债合并进来仍要 ≤ 估计轮数。
3. **债**：一次压缩的一次性成本记为债，之后每轮按「每轮少花」偿还（state.ts 同款）；没还完又压，合并门槛卡住——「压完你就不聊了」的损失就靠它防。

唯一的「线」是**窗口保护线 = 窗口 − 16384**（`windowReserveTokens`，economics.ts:17）：过线无条件压，不算经济账。聊天里模型可能始终不调工具，所以每个 provider 请求前插件也查这条线，过了就在消息里下强制指令。1M 窗口上核心 82%（820k）比它先到，那个归核心管。

两处与上游不同的适配（只有这两处）：

1. 上游的估计轮数 = 剩余计划步数 × 每步实测轮数，因为它有 plan 工具。聊天没有计划，改用窗口封顶值；增量实测不出来就退回 `horizon_unavailable`，不瞎猜。
2. 上游用原生压缩，一次性成本只有缓存重写溢价。本插件的压缩是一次真实的摘要模型调用，所以一次性成本里加了归档段读一遍和 memo 写一遍的费用。

memo 按 1000 tokens 估算（`DEFAULT_NATIVE_SUMMARY_TOKEN_ESTIMATE`，extension.ts:36），压完记实测值。

## 窗口从哪来

四级：provider 配置 → models.dev → OpenRouter 目录 → `fallback_max_tokens`。第三级只写内存，不动 `cmd_config.json`。估计轮数和窗口保护线都按窗口算，窗口虚高判定就虚松，所以面板上标着当前这个数来自哪一级，上游会限流时自己留意目录那级。

## 模型怎么知道该压

每轮在用户消息末尾注入一行状态：

```
[context: 当前 45200 / 模型上限 256000 tokens]
```

工具的说明里写着：话题聊完、彻底翻篇就调。插件接到调用先判账，不划算就退回一句原因（台账同步记一笔），模型接着回答用户，什么内容都没动。过窗口保护线时状态行换成强制指令：本轮先调工具再回答。

判断这个插件值不值得开，看台账的压缩率和退回原因分布，面板顶部就是这个数。

## 影子模式

`dry_run` 默认开。判账照算，不调摘要，不改历史，台账在 `data/plugin_data/astrbot_plugin_astrsol/ledger.jsonl`：

| outcome | 含义 |
|---|---|
| `compacted` | 真压了 |
| `dry_run` | 影子模式，本该压 |
| `empty_summary` | 摘要模型返回空 |
| `non_positive_saving` | 归档段还没 memo 长，压不出节省 |
| `horizon_unavailable` | 还没有增速数据，估不出还能聊几轮 |
| `price_unavailable` | 拿不到价目，经济账缺席 |
| `deferred_economic` | 打平轮数 > 估计轮数 |
| `deferred_subsequent_margin` | 距上次压缩太近，×1.5 门槛够不着 |
| `deferred_carried_debt` | 上一次的债没还完 |

先看压缩率和退回原因分布，看明白了再关 `dry_run`。

## 机制

按整轮切：最近 `keep_recent` 的整轮原样保留，当前这轮永远保留，更早的交给摘要模型。system prompt 不动。上次的摘要下次一起重摘，不会越积越多。

状态行放在用户消息末尾、跟着历史落盘，是为了不动上游前缀缓存。别去摘它，摘了下一轮前缀和缓存对不上。

## 限制

- 依赖模型自觉在话题边界调用，需要 function calling。乱调的代价是零：判账不花钱，不划算原样退回
- 人格白名单会屏蔽工具，面板会告警
- WebChat 会显示工具调用过程，其他平台不可见
- 压缩耗时叠加在回复前，靠便宜摘要模型压着，`tool_call_timeout` 兜底，超时零改写
- 价目是 OpenRouter 官方牌价，公式是比值，货币单位约得掉，两个模型渠道溢价比例接近就仍然成立
- 别的插件停掉事件会导致整轮不落盘，压缩结果跟着丢
- 压缩后第一轮缓存要重建，这是机制生来要付的钱，已计入一次性成本
