# SoL-Astr

给模型一个压缩工具。话题聊完了它自己调 `sol_astr_compact`，把早前的对话换成一段摘要，省后面的缓存输入钱。移植自 NVIDIA Research [SoL-Pi](https://nvlabs.github.io/SoL-Pi) 的 Online Context Compact。

## 和内置压缩的关系

插件管早压，内置 82% 管防爆，两层都留着。

- 内置 82% 压缩：别关，那是兜底
- 单条工具结果 overflow：不受影响
- 按轮截断 `max_turns`：不是 -1 会抢在压缩前面丢轮，面板会告警，插件不动它

## 面板

插件页打开 dashboard，全部信息都在：

- 压缩线是多少、怎么算的，窗口这个数来自哪一级
- 上下文标尺：保留段、压缩线、内置兜底线和各会话真实用量画在同一根轴
- 两个模型解析到了 OpenRouter 哪条目录、四个价格、几次请求回本
- 模拟器：拖参数看压缩线怎么变，满意了直接写进配置
- 台账：触发率、outcome 分布、归档段分布、每次压缩的前后对比和耗时
- 告警：下面三件能让插件悄悄失效的事

1. 人格 `tools` 白名单没加 `sol_astr_compact`，模型根本看不到工具
2. `max_turns` 不是 -1，按轮截断抢在压缩前丢轮
3. 摘要模型贵到分母 ≤ 0，压一次赔一次

## 配置

摘要模型和压缩提示词不在插件里，读核心「上下文管理策略」那两项，留空就回落当前聊天模型和插件默认。压缩模型挑个比主模型便宜快的：摘要是回复前同步做的，让主模型干这活，用户每轮多等十几秒，账也算不回来。

插件自己的六项，面板里能改：

| 配置项 | 默认 | 说明 |
|---|---|---|
| `enable_compact` | false | 总开关 |
| `dry_run` | true | 影子模式，只记账不调摘要 |
| `keep_recent_tokens` | 0 | 保留段，0 = 按窗口自动 |
| `min_archive_tokens` | 0 | 最小归档段，0 = 按压缩线自动 |
| `target_turns` | 5 | 几轮内打平才允许压 |
| `strip_tool_trace` | true | 压缩轮落盘前删掉工具调用记录 |

## 压缩线怎么定

先对齐名词。一次压缩把上下文切成三段：**保留段**是最近的几轮，原样不动；**归档段**是保留段之前的全部旧对话，整段交给摘要模型，压成一段摘要替换回去；当前这轮永远保留。压缩线 = 保留段 + 最小归档段，意思是归档段攒够这么大才允许压。

钱花出去不会回来，所以没有什么「回本」，只有两条烧钱曲线比谁缓：

- 不压：每轮按缓存读价重读整个上下文，越聊越贵
- 压：一次性付 `C = (K+M)(Pi−Pc+Pw) + A·Si + M·So`，之后每轮少花 `S = A×Pc`

聊到第 `C/S` 轮，两条线的累计花费打平；再往后，压的那条一直更低。`C/S` 随归档段变大单调下降——固定成本被摊薄——所以线画高了经济上只会更划算。它的代价在另一头：话题早早结束、没到线的对话一次都压不到，那些轮次一直在按全价缓存读烧钱。

三条线定一条：先画许可线，摘要模型装不下就提前到摘要窗口线，还低于经济线就抬到经济线。面板来源会写明当前是「按窗口 / 摘要模型窗口 / 经济线」。

1. **经济线**（价格反推，下限）：让 `N×S − C > 0` 的最小归档段。N 是 `target_turns`，不是预测，是押注纪律：一次压缩的最坏情况是压完你再也不聊、白花这一次的 C，N 就是给这笔押注定的上限——几轮内打平不了，这套组合就不配压。低于经济线压缩是赔钱买卖，线比它低会被它抬上来。`N×Pc ≤ Si` 时它不存在：摘要模型读一遍比 N 轮少花的还贵，压多少次都赔，面板直接报错。
2. **许可线**（窗口 × 0.72，默认画线）：0.72 = 内置兜底 82% − 10% 反应区，写死在代码里。反应区是给模型的：过线后不一定立刻调工具，磨蹭几轮也撞不上兜底。它比经济线高时，高出来的部分是在用钱换原文——话题 100k 结束了、线在 720k，那 100k → 720k 的每一轮都在多烧 `A×Pc`，这就是多用窗口的价签。想自己定线就手填 `min_archive_tokens`。
3. **摘要窗口线**（摘要模型窗口 × 80%，上限）：归档段得整段塞进摘要模型，装不下时线提前。

保留段管对话质量，价格不介入：`min(窗口 × 15%, 40000)`。

## 窗口从哪来

四级：provider 配置 → models.dev → OpenRouter 目录 → `fallback_max_tokens`。第三级只写内存，不动 `cmd_config.json`。压缩线和保留段都按窗口画，窗口虚高线就虚高，所以面板上标着当前这个数来自哪一级，上游会限流时自己留意目录那级。

## 模型怎么知道该压

每轮在用户消息末尾注入一行状态，三个数都给：

```
[context: 当前 45200 / 压缩线 98400 / 模型上限 256000 tokens]
```

只给前两个，模型会把压缩线当容量上限，用掉 105k 写成 `105000/98400` 看着像溢出，它就开始莫名其妙惜字如金。上限给了，它才知道 105k 其实还很宽裕。

过线时状态行会补一句：话题聊完了就调 `sol_astr_compact`，还在聊同一个就先放着。它也可能就是不调，台账记 `not_called`：

```
触发率 = 调用次数 / (调用次数 + not_called)
```

触发率不行，这插件就别开了，面板顶部就是这个数。

## 影子模式

`dry_run` 默认开。全流程照跑，不调摘要，不改历史，台账在 `data/plugin_data/astrbot_plugin_astrsol/ledger.jsonl`：

| outcome | 含义 |
|---|---|
| `not_called` | 够格了，这轮没调 |
| `too_small` | 调了，归档段不够大 |
| `dry_run` | 影子模式，本该压 |
| `empty_summary` | 摘要模型返回空 |
| `compacted` | 真压了 |

先看触发率和归档段分布，看明白了再关 `dry_run`。

## 机制

按整轮切：最近 `keep_recent` 的整轮原样保留，当前这轮永远保留，更早的交给摘要模型。system prompt 不动。上次的摘要下次一起重摘，不会越积越多。

状态行放在用户消息末尾、跟着历史落盘，是为了不动上游前缀缓存。别去摘它，摘了下一轮前缀和缓存对不上。

## 限制

- 依赖模型自觉调用，需要 function calling。不调记 `not_called`；乱调的代价是旧内容变摘要，保留段原样不动，归档段不够大会被挡回去
- 人格白名单会屏蔽工具，面板会告警
- WebChat 会显示工具调用过程，其他平台不可见
- 压缩耗时叠加在回复前，靠便宜摘要模型压着，`tool_call_timeout` 兜底，超时零改写
- 价目是 OpenRouter 官方牌价，公式是比值，货币单位约得掉，两个模型渠道溢价比例接近就仍然成立
- 别的插件停掉事件会导致整轮不落盘，压缩结果跟着丢
- 压缩后第一轮缓存要重建，这是机制生来要付的钱，已计入公式
