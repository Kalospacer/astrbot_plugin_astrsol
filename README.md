# SoL-Astr

给 LLM 一个「压缩上下文」的工具。它自己判断旧话题已经聊完了就调用，工具在 agent 循环内部把早前的对话换成一段摘要，同一轮的续写请求立刻用上压缩后的上下文，轮末由 AstrBot 正常落盘。

移植自 NVIDIA Research [SoL-Pi](https://nvlabs.github.io/SoL-Pi) 的 Online Context Compact：**在语义边界压缩，而不是等上下文快满了才压**。

## 和内置机制的关系

```
[本插件] 语义压缩：LLM 在话题边界自主调用，阈值按模型窗口自动算
   ↓ 目标是让上下文尽量到不了 82%
[内置] 82% 压缩：防爆窗兜底，保留，不要关
[内置] 单条工具结果 overflow：正交，不受影响
[核心配置] 按轮截断 max_turns：非 -1 时本插件会告警，但不会替你改
```

## 配置

**摘要模型和压缩提示词不在插件里配**，直接用核心「上下文管理策略」里已有的两项：

| 核心配置项 | 本插件怎么用 |
|---|---|
| 用于上下文压缩的模型提供商 ID | 摘要模型。留空或不可用时回落当前聊天模型，行为与内置压缩器一致 |
| 上下文压缩提示词 | 摘要指令。留空才用插件默认。包裹方式与内置逐字相同，所以同一条提示词在两边表现一样 |
| 压缩前最多保留对话轮数 | 不是 -1 时插件会告警——按轮截断会抢在压缩之前丢消息 |

**压缩模型一定要指一个比主聊天模型便宜、更快的**。摘要是在回复用户之前同步做的，用主模型意味着用户多等十几秒、这次压缩还大概率不回本。

插件自己只有这几项：

| 配置项 | 默认 | 说明 |
|---|---|---|
| `enable_compact` | false | 总开关 |
| `dry_run` | true | 影子模式：只记台账，不调摘要、不改写上下文 |
| `keep_recent_tokens` | 0（自动） | 压缩时按整轮保留的最近上下文 |
| `min_archive_tokens` | 0（自动） | 归档段小于这个数就不压 |
| `strip_tool_trace` | true | 压缩成功的那轮，落盘前删掉工具调用记录 |

注意核心的「压缩时保留最近上下文比例」（`keep_recent_ratio`，默认 0.15）只管内置压缩，本插件用的是上面的绝对值 `keep_recent_tokens`。比例制在大窗口模型上会失效——256k 窗口的 15% 是 38k，看着差不多，但换个模型就全变了。

### 模型怎么知道该压了

这是整套机制最关键、也最容易被忽略的一环。压缩由 LLM 自己发起，那它凭什么知道现在该压？它需要三样东西，缺一样就要么从不调用、要么乱调：

1. **话题聊完没有** —— 模型自己判断，它看得见完整对话，这是它擅长的。
2. **上下文够不够大** —— 模型判断不了。裸给一个「45200 tokens」它无从知道算大算小，对 1M 窗口是零头，对 32k 是快爆了。所以**由插件算**。
3. **够大之后该干什么** —— 得直说。

插件每轮在用户消息尾部注入一行状态，把 2 和 3 一起给出去：

```
没过线： [context: 当前 45200 / 压缩线 98400 / 模型上限 256000 tokens]

过线了： [context: 当前 105000 / 压缩线 98400 / 模型上限 256000 tokens —— 用量过压缩线了。
        要是刚才那个话题聊完了、也没留下什么没办完的事，就调 sol_astr_compact 把早前的
        记录收一收。还在聊同一件事就先放着。]
```

**三个数必须都给**。只写「当前/压缩线」模型会把压缩线当成容量上限——256k 的窗口用掉 105k 明明还很宽裕，写成 `105000/98400` 却像是已经溢出了，模型会莫名其妙地开始惜字如金。

**体积判断归插件，语义判断归模型**，各做各擅长的。工具描述里也写明了两个条件必须同时满足。

模型仍然可能就是不调——这是这类设计无法从根上消除的风险，只能量化。所以台账里除了实际调用，还会记录**「够格却没调」**（`outcome: not_called`）：

```
触发率 = 调用次数 / (调用次数 + not_called 次数)
```

这个数是判断插件该不该继续用的首要依据。低得离谱就说明信号不够强或者模型不配合。

### 阈值怎么来的：按窗口自动算

两个阈值默认填 0，表示自动。窗口直接读 AstrBot 已经解析好的结果（provider 配置 → models.dev 元数据 → 你配的「上下文窗口兜底值」），插件不自己探测。

```
保留段   = min(窗口 × 15%, 40000)
最小归档 = min(窗口 × 25%, 60000)
起压门槛 = 两者之和
```

| 模型窗口 | 保留 | 归档 | 起压于 | 内置 82% 兜底线 |
|---|---|---|---|---|
| 32k | 4800 | 8000 | 12800 | 26240 |
| 128k | 19200 | 32000 | 51200 | 104960 |
| 256k | 38400 | 60000 | 98400 | 209920 |
| 1M | 40000 | 60000 | 100000 | 820000 |

**为什么是「比例和绝对值取小」**：纯绝对值在小窗口上是死值（32k 的模型永远够不到 100k 门槛，插件等于没装）；纯比例在大窗口上等于没压（1M 的 15% 是 150k，压完还剩 150k）。取小同时避开两头。

**为什么门槛定在窗口的 40%**：起压线必须明显低于内置 82% 兜底线，否则每次都是内置先动手、插件没机会在语义边界上压。40% 留了一倍余量。

### 想自己调的话

填非 0 的值就会覆盖自动计算。调之前先看一组账——模拟 200 轮闲聊（每轮涨 1.5k、每 15 轮一个话题边界）在 256k 窗口下的总成本：

| 保留 / 归档 | 起压于 | 压缩次数 | 总成本 | 省下 | 单次回本 |
|---|---|---|---|---|---|
| 不压缩 | — | 0 | 62.90 元 | — | — |
| 40k / 100k | 140k | 2 | 33.21 元 | 29.69 元 | 1.6 轮 |
| **≈自动值** | **≈98k** | **3** | **28.36 元** | **34.54 元** | 2.5 轮 |
| 40k / 40k | 80k | 5 | 24.91 元 | 37.99 元 | 3.5 轮 |
| 20k / 30k | 50k | 6 | 16.92 元 | 45.98 元 | 2.5 轮 |

注意 40k/100k 的**单次回本最漂亮，总成本却最差**——它被自动值严格支配：保留段一样大（对话质量相同），只是压得更少、烧得更多。「几轮回本」只算了压缩动作本身的投入产出，没算**不压缩期间每轮都在烧的钱**，而后者是线性累积的。

所以纯看成本，门槛应该更低。没定得更低是因为两个折不成钱的代价：**保留段太小 bot 会明显变笨**，以及**压完用户就不聊了那次纯亏**（模拟假设一直聊下去，而闲聊常常几句就停）。要更省就往下调归档段，不要往上。

配置改完在插件页点重载。

### 先跑影子模式

`dry_run` 默认开着。开启插件后先这样跑几天真实聊天，台账在 `data/plugin_data/astrbot_plugin_astrsol/ledger.jsonl`，每次工具调用一条：

```
ts, umo, cid, outcome, total_tokens, archive_tokens, keep_tokens,
archive_messages, keep_messages, keep_recent, min_archive,
memo_tokens, summarizer_*, duration_ms
```

`outcome` 五种：

| 值 | 含义 |
|---|---|
| `not_called` | 上下文够格了，但模型这一轮没调工具 |
| `too_small` | 模型调了，但归档段不够大 |
| `dry_run` | 影子模式，本该压缩 |
| `empty_summary` | 摘要模型返回空，零改写 |
| `compacted` | 真的压了 |

先算**触发率** = `dry_run` / (`dry_run` + `not_called`)，这是判断插件值不值得开的首要依据。再看 `archive_tokens` 的分布，决定要不要手动调阈值。看明白了再把 `dry_run` 关掉。

## 工作方式

每轮请求会在用户消息**末尾**追加一行 context 状态，N 优先取上一轮 API 返回的真实用量。放在末尾而不是 system prompt，是为了不动上游的前缀缓存；这一行会跟着历史落盘，**不要想着把它摘掉**，摘掉反而会让下一轮的前缀和缓存对不上。

模型调用工具后，插件按整轮切分上下文：最近 `keep_recent_tokens` 的整轮原样保留，当前这轮永远保留，更早的部分交给摘要模型压成一段，替换回去。`messages[0]` 的 system prompt 绝不动。上一次压缩产生的摘要在下次压缩时会被一并重摘，所以摘要不会越积越多。

## 已知限制

- **依赖模型自觉调用**。模型需要支持 function calling。它不调 = 功能不触发，没有副作用，但台账会记 `not_called`，跑一段时间就知道触发率；乱调 = 旧内容变成摘要而非丢失，保留段原样不动，且归档段不够大时会被直接挡回去。
- **人格白名单会屏蔽本工具**。如果人格里显式配了 `tools` 列表，要自己把 `sol_astr_compact` 加进去，否则工具根本不会出现。
- **WebChat 会显示工具调用过程**，它无视 `show_tool_use_status` 开关。其他平台默认不可见。
- **压缩耗时叠加在回复之前**。非流式下用户干等摘要，流式下正文已经发出、卡的是收尾。靠便宜摘要模型控制，超时由 AstrBot 的 `tool_call_timeout` 兜底，超时即零改写。
- **别的插件停掉事件会导致整轮不落盘**，压缩结果跟着一起丢。不是数据损坏，但日志里要能看出来。
- **压缩后的第一轮缓存要重建**，这是这套机制生来就要付的钱。
