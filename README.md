# SoL-Astr

给 LLM 一个「压缩上下文」的工具。它自己判断旧话题已经聊完了就调用，工具在 agent 循环内部把早前的对话换成一段摘要，同一轮的续写请求立刻用上压缩后的上下文，轮末由 AstrBot 正常落盘。

移植自 NVIDIA Research [SoL-Pi](https://nvlabs.github.io/SoL-Pi) 的 Online Context Compact：**在语义边界压缩，而不是等上下文快满了才压**。

## 和内置机制的关系

```
[本插件] 语义压缩：LLM 在话题边界自主调用，保留最近 40k、归档段满 60k 才压（起压 100k）
   ↓ 目标是让上下文尽量到不了 82%
[内置] 82% 压缩：防爆窗兜底，保留，不要关
[内置] 单条工具结果 overflow：正交，不受影响
[核心配置] 按轮截断 max_turns：非 -1 时本插件会告警，但不会替你改
```

## 配置

**摘要模型和压缩提示词不在插件里配**，直接用核心「上下文管理策略」里已有的两项：

| 核心配置项 | 本插件怎么用 |
|---|---|
| 用于上下文压缩的模型提供商 ID | 摘要模型。留空或不可用时回落当前聊天模型，行为与内置压缩器一致 |
| 上下文压缩提示词 | 摘要指令。留空才用插件默认。包裹方式与内置逐字相同，所以同一条提示词在两边表现一样 |
| 压缩前最多保留对话轮数 | 不是 -1 时插件会告警——按轮截断会抢在压缩之前丢消息 |

**压缩模型一定要指一个比主聊天模型便宜、更快的**。摘要是在回复用户之前同步做的，用主模型意味着用户多等十几秒、这次压缩还大概率不回本。

插件自己只有这几项：

| 配置项 | 默认 | 说明 |
|---|---|---|
| `enable_compact` | false | 总开关 |
| `dry_run` | true | 影子模式：只记台账，不调摘要、不改写上下文 |
| `keep_recent_tokens` | 40000 | 压缩时按整轮保留的最近上下文，绝对值 |
| `min_archive_tokens` | 60000 | 归档段小于这个数就不压 |
| `strip_tool_trace` | true | 压缩成功的那轮，落盘前删掉工具调用记录 |

注意核心的「压缩时保留最近上下文比例」（`keep_recent_ratio`，默认 0.15）只管内置压缩，本插件用的是上面的绝对值 `keep_recent_tokens`。比例制在大窗口模型上会失效——256k 窗口的 15% 是 38k，看着差不多，但换个模型就全变了。

### 这两个默认值是怎么定的

两者相加就是**实际起压门槛**：40000 + 60000 = 100k 以下压不动。

定值时不要只看「压这一次几轮回本」——那个指标只算了压缩动作的投入产出，没算**不压缩期间每轮都在烧的钱**。门槛越高，等待期越长，而等待期的浪费是线性累积的。模拟 200 轮闲聊（每轮涨 1.5k，每 15 轮一个话题边界）：

| 保留 / 归档 | 起压于 | 压缩次数 | 总成本 | 省下 | 单次回本 |
|---|---|---|---|---|---|
| 不压缩 | — | 0 | 62.90 元 | — | — |
| 40k / 100k | 140k | 2 | 33.21 元 | 29.69 元 | 1.6 轮 |
| **40k / 60k** | **100k** | **3** | **28.36 元** | **34.54 元** | 2.5 轮 |
| 40k / 40k | 80k | 5 | 24.91 元 | 37.99 元 | 3.5 轮 |
| 20k / 30k | 50k | 6 | 16.92 元 | 45.98 元 | 2.5 轮 |

注意 40k/100k 的单次回本最漂亮，总成本却最差——它被 40k/60k 严格支配：保留段一样大（对话质量相同），只是压得更少、烧得更多。

纯看成本应该把门槛压到更低。没那么做是因为两个折不成钱的代价：**保留段太小 bot 会明显变笨**（20k 只剩十几轮原文），以及**压完用户就不聊了那次就纯亏**（模拟里假设一直聊下去，没建模会话结束，而闲聊经常是几句就停）。40k 是保留段的质量底线，60k 是在此约束下的成本较优点。

要更省就**往下调归档段**（改成 40000），不要往上调。窗口小于 256k 的部署两个数都要按比例往下调。真实的话题边界密度得看台账，`too_small` 占压倒多数就说明门槛偏高。

配置改完在插件页点重载。

### 先跑影子模式

`dry_run` 默认开着。开启插件后先这样跑几天真实聊天，台账在 `data/plugin_data/astrbot_plugin_astrsol/ledger.jsonl`，每次工具调用一条：

```
ts, umo, cid, outcome, total_tokens, archive_tokens, keep_tokens,
archive_messages, keep_messages, memo_tokens, summarizer_*, duration_ms
```

`outcome` 有 `too_small` / `dry_run` / `empty_summary` / `compacted` 四种。先看两个数：**模型多久调一次工具**，以及**调用时归档段真实多大**。触发率太低就说明这个插件在你的使用场景里不值得开。看明白了再把 `dry_run` 关掉。

## 工作方式

每轮请求会在用户消息**末尾**追加一行 `[context: N tokens]`，N 优先取上一轮 API 返回的真实用量。放在末尾而不是 system prompt，是为了不动上游的前缀缓存；这一行会跟着历史落盘，**不要想着把它摘掉**，摘掉反而会让下一轮的前缀和缓存对不上。

模型调用工具后，插件按整轮切分上下文：最近 `keep_recent_tokens` 的整轮原样保留，当前这轮永远保留，更早的部分交给摘要模型压成一段，替换回去。`messages[0]` 的 system prompt 绝不动。上一次压缩产生的摘要在下次压缩时会被一并重摘，所以摘要不会越积越多。

## 已知限制

- **依赖模型自觉调用**。模型需要支持 function calling。它不调 = 功能不触发，没有副作用；乱调 = 旧内容变成摘要而非丢失，最近 20k 原样保留，损失可控。
- **人格白名单会屏蔽本工具**。如果人格里显式配了 `tools` 列表，要自己把 `sol_astr_compact` 加进去，否则工具根本不会出现。
- **WebChat 会显示工具调用过程**，它无视 `show_tool_use_status` 开关。其他平台默认不可见。
- **压缩耗时叠加在回复之前**。非流式下用户干等摘要，流式下正文已经发出、卡的是收尾。靠便宜摘要模型控制，超时由 AstrBot 的 `tool_call_timeout` 兜底，超时即零改写。
- **别的插件停掉事件会导致整轮不落盘**，压缩结果跟着一起丢。不是数据损坏，但日志里要能看出来。
- **压缩后的第一轮缓存要重建**，这是这套机制生来就要付的钱。
